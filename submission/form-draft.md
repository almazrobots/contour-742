## 3. Как подготовить чистовой репозиторий

Название **contour-742** нейтральное и не содержит названия команды или конкурса. При этом владелец `almazrobots`, ссылки на стенды, содержимое файлов и автор нового коммита могут раскрывать связь с проектом. Нейтральное название не обеспечивает анонимность.

Рабочий репозиторий остаётся на прежнем `origin`. В новый репозиторий исходная история не переносилась; код пока не загружен, потому что параллельные сессии ещё работают.

### Порядок подготовки после завершения работ

1. Согласовать окончательный срез с работающими сессиями. Сохранить его исходный commit ID во внутреннем журнале и отдельно учесть нужные незакоммиченные файлы. Папка «Презентация» сейчас не содержит отслеживаемых Git файлов: обычный экспорт коммита может её не включить.
2. Создать отдельный каталог вне рабочего дерева. Перенести в него только явно отобранные файлы продукта, инструкций, зависимостей, тестов и безопасных демонстрационных данных. Проверить необходимые файлы сборки и lock-файлы. Не копировать рабочий каталог целиком.
3. Проверить содержимое отобранных файлов сканером секретов и вручную. Проверять не только имена: ключи, пароли, токены, строки подключения и внутренние адреса могут находиться в исходниках, отчётах, скриптах и документах. Не переносить автоматически существующие исключения `.gitleaksignore`.
4. Проверить презентацию, видео, PDF, изображения и метаданные офисных файлов: отсутствие реальных документов, персональных данных, секретов на экране и внутренних комментариев. Сканер исходного текста не заменяет такую проверку.
5. Исправить ссылки на старый репозиторий, локальные абсолютные пути и недоступные внутренние ресурсы. Сохранить необходимые лицензии и атрибуцию сторонних компонентов. Добавить шаблоны конфигурации с фиктивными значениями и инструкцию получения собственных ключей.
6. В новом каталоге выполнить `git init -b main`, проверить выбранные для коммита файлы, создать один начальный коммит и подключить `https://github.com/almazrobots/contour-742.git`. Не использовать `clone --mirror`, перенос `.git`, старых веток или тегов. Проверить имя и email автора коммита; при необходимости использовать свой GitHub noreply email.
7. Загрузить этот снимок в приватный репозиторий. Из свежего клона проверить сборку, запуск по README и заявленные демонстрационные сценарии. Проверить, что история содержит только новый начальный коммит и не появились старые ветки/теги.
8. После проверки финального состава сделать новый репозиторий публичным и проверить все ссылки в приватном окне браузера. Не менять видимость исходного рабочего репозитория.

**Не включать по умолчанию:** `.git`, `.secrets`, реальные `.env`, ключи и сертификаты с приватными ключами, `var`, дампы баз, логи, браузерные профили и состояния авторизации, `.playwright-mcp`, временные `out`, кэши, `node_modules`, виртуальные окружения, внутренние рабочие заметки и отчёты без проверки. Файлы `.env.example` допустимы после проверки значений. Отдельные синтетические тестовые ключи допустимы только после подтверждения, что они не дают доступа к реальным системам.

**Данные корпуса:** согласно [ADR-0002](../docs/adr/ADR-0002-corpus-legal-regime.md) реальные документы corpus-ABC, извлечённый из них текст и фикстуры не допускаются в репозиторий; публичные демо и скриншоты используют синтетику. Для материалов организатора и производных наборов отдельно проверить разрешённый режим распространения. Не переносить целиком `INPUT`, `ТЗ` и `data` без отбора.

Отсутствие старой Git-истории не исключает секреты в текущих файлах. Если найдены действующие утёкшие учётные данные, их нужно отозвать или заменить, а не только удалить из нового снимка.

## 4. Как оформить материалы для жюри

В документации должны легко находиться: назначение решения; быстрый старт; вход и роли; сценарий «документы → сравнение → доказательство → решение инспектора → протокол»; архитектура; применяемые модели; воспроизведение тестов; ограничения. Не заявлять полное покрытие 132 параметров или выполнение всех требований только на основании наличия матрицы и кода — приводить подтверждённые результаты финального среза.

В `submission/README.md` разместить ссылки на презентацию, видео, CPU-демо, GPU-прототип, руководство и отобранный отчёт о проверках. Указать, где интерактивный стенд, а где просмотр результатов; какие данные синтетические; какие функции пока недоступны. Эта страница будет единой ссылкой поля «Дополнительные материалы».

Для доступа к прототипу подготовить отдельную учётную запись жюри с нужными правами. Учесть оба уровня входа: HTTP-защиту сайта и вход в приложение. Пароли не помещать в публичный Git, презентацию или эту памятку. Передать их через предусмотренный организатором непубличный канал. Если такого канала нет, заранее решить вопрос с гостевым доступом к изолированному демо на синтетике.
