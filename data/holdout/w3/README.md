# Отложенный состязательный набор W3

## Назначение

Независимая проверка 14 параметров волны W3 (план `docs/plan/W3-ПЛАН.md`, п. 2 «Параметр засчитан, когда»):
M-033, M-043, M-048, M-053, M-063, M-070, M-082, M-087, M-091, M-092, M-095, M-096, M-106, M-122.
Набор проверяет **реализацию**, а не повторяет её: ожидаемые ответы выведены только из Матрицы
(`docs/research/TO-BE-операции-сравнения.md`, §11 карточки CMP-06/07/09/17/18/22/23/25, §13.1 таблица решений,
§17 строки параметров), из норм (СП 1.13130, СП 59.13330, СП 42/СП 34 и др. — по общим знаниям, пороги
сверять с Normative_Base) и из здравого смысла инспектора. Код веток W3 при составлении не открывался.

Все тексты **выдуманы**: адресов, шифров, названий объектов и фрагментов корпуса нет (ADR-0002).

## Правило «исполнители не видят до замера»

- Набор живёт только в ветке `feat/w3-plan`. Ветки `feat/w3-quantity`, `feat/w3-presence`, `feat/w3-schedule-docs`,
  `feat/w3-orient` его не сливают, не копируют и не подгоняют под него правила.
- Исполнитель ветки не читает `cases.jsonl` до замера. Замер делает тимлид T-210 по коммиту ветки.
- После замера случаи, на которых ветку чинили, уходят в обучающую синтетику; для следующего замера набор
  пополняется новыми случаями — иначе он перестаёт быть отложенным.

## Формат `cases.jsonl`

Одна строка — один случай:

| Поле | Смысл |
|---|---|
| `id` | `W3-M033-01` — параметр и номер |
| `param` | код параметра Матрицы |
| `stages.PD / RD / ID` | фрагменты стадий `{discipline, text}`; строки таблиц — через `\|`, строки — через `\n` |
| `expected.status` | CANDIDATE, NEGATIVE_VERIFIED, MISSING_EVIDENCE, NOT_COMPARABLE, NOT_APPLICABLE, SUSPICION |
| `expected.accept` | допустимые альтернативы для спорных случаев (ответ из списка — не ошибка) |
| `adversarial` | что ловит случай; `null` — базовый случай |
| `why` | обоснование ожидаемого статуса |

Пустой список стадии — **документ стадии не предоставлен**. Для параметров, сравнивающих ПД и РД, пустая РД даёт
MISSING_EVIDENCE; для M-096 акты ищутся в ИД, пустая ИД — MISSING_EVIDENCE. Для ППР (M-091, M-092, M-095, M-082,
M-087) ППР и график лежат в стадии RD.

## Как считать

Ответ системы по случаю — один статус. Верен, если он равен `expected.status` или входит в `expected.accept`.

1. **FP-нарушение (главная метрика, цель 0).** Система выдала CANDIDATE, а CANDIDATE нет ни в `status`, ни
   в `accept`. Считается числом и долей от случаев, где CANDIDATE не ожидался. Любое FP-нарушение — параметр
   не засчитан (план W3, п. 2).
2. **Recall по CANDIDATE.** Доля случаев с `expected.status = CANDIDATE`, где система выдала CANDIDATE.
   Ответ из `accept` (обычно SUSPICION) Recall не повышает, но и FP не является.
3. **Доля воздержаний.** Доля ответов MISSING_EVIDENCE, NOT_COMPARABLE, NOT_APPLICABLE, SUSPICION среди всех
   ответов системы; публикуется рядом с долей воздержаний эталона (57/189 = 30 %). Сильно выше — система
   прячется; сильно ниже — угадывает.
4. Дополнительно — точность статуса (с учётом `accept`) по каждому параметру и по каждому виду ловушки.

Метрики публикуются по параметру и в целом, с размером выборки; при 13–14 случаях на параметр интервал Уилсона
широк — это набор-сторож, а не оценка качества в процентах.
