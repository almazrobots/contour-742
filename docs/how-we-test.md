# Как мы тестируем

**TL;DR.** Предметная логика (выбор редакции, сравнение, статусы, жизненный цикл, GOLD) написана
чистыми функциями в `apps/api/src/domain` и покрыта модульными тестами и мутациями. Сквозной тест
поднимает настоящий ML-сервис и прогоняет три синтетических объекта против `answer-key.json`.
Каждое правило сервиса из `03-services.md` связано с тестом через `model.yaml` → `impl`;
`pnpm trace:check` падает, если тест или символ исчез.

## Эшелоны

- **L1 функциональные** — `domain.test.ts`, `ml/tests` (`l1_functional`). Название теста = ссылка в трассе.
- **L2 независимая сверка** — e2e против ключа ответов генератора синтетики (`data/synth/*/answer-key.json`).
- **L3 граничные** — `domain-boundaries.test.ts`: порог ровно на границе, пустые источники, 50/200 МБ.
- **L4 отказы** — очередь (повторы и onDead), недоступность «РиН» с повторами 1/5/15 мин, параллельный pdfium;
  конкурентность БД (T-107): параллельные тики sync_jobs, дубли статусов предписаний, захват пакета «РиН», выпуск отчёта,
  перевод гипотезы — одна запись; откат транзакции и точки сохранения (`db.test.ts`).
- **L5 property** — не заведены; кандидат — `evaluate` на fast-check.
- **L6 враждебные данные** — XXE и billion laughs, битый PDF, подмена формата, path traversal в ML.
- **L7 дисциплина** — zod на границах API, громкая проверка окружения в `config.ts`; гейт висящих промисов
  `pnpm check:promises` (async без await/return/void — дефект; самопроверка на фикстуре, где гейт обязан краснеть).

**База в тестах (ADR-0003).** Каждый тест — своя база PostgreSQL: `await openDb("memory")` поднимает PGlite 0.5.8
(PostgreSQL 18.3) из снимка шаблона за миллисекунды. Паритет: `INSPECTOR_TEST_DATABASE_URL=postgres://…` — тот же набор
на сервере PostgreSQL 18, каждая база — отдельная схема, удаляется при `close()`. Релиз не выходит без зелёного паритета.
- **L8 регрессии и мутации** — баг закрыт, когда его вход стал тестом; Stryker (TS) и mutmut (Python).

## Критичные модули и пороги

`compare.ts`, `lifecycle.ts`, `revisions.ts`, `completeness.ts`: мутационный скор ≥ 70 % (break в
`stryker.config.mjs`), покрытие строк ≥ 75 %. Пороги можно только поднимать.

Итерация 4: проверка электронной подписи (`domain/signature.ts`, `services/signature.ts`) — критичный модуль
(подписи, qa-standard), тот же порог 70 %, факт — 99 % и 89 %. Автозабор из «РиН» (`domain/rin-pull.ts`,
`services/rin-pull.ts`) и журнал ответа (`domain/access-log.ts`) гоняются тем же порогом.

## Cross-cutting

- Синтетика — единственный источник фикстур (ADR-0002). Корпус из Яндекс.Диска в тесты не попадает.
- Мутационные прогоны по одному модулю за раз, каждый меньше минуты (правило №0 рабочей машины).
- Stryker работает с Vitest 3: с Vitest 5 мутанты не активируются (найдено 2026-09-24).

## Зависимости

`pnpm audit` и `uv pip` + `pip-audit` — перед выкатом. torch и CUDA-стек на мак не ставятся.

## The adequacy line

Тестов хватает, когда каждое правило `03-services.md` в статусе ✅ в трассе имеет тест, а
мутационный скор критичных модулей не ниже порога. Качество ML-извлечения на реальных сканах
(метрики ТЗ §14) этой линией не покрывается — это GPU-стенд со скрытым тестом организатора.

## Q-уровень

Q1: гейт локальный, CI нет. До Q2 нужен workflow «тесты → сборка», который блокирует выкат.
