## Отдельный доступ к S3

Владелец бакета создаёт отдельный service account для CPU-копии и выдаёт чтение только нужного бакета/префиксов: получение объектов и, если требуется проверке, ограниченный ListBucket. Запись, удаление и администрирование не нужны. Не копируйте единственный личный ключ владельца. Секреты передаются отдельно защищённым каналом, с возможностью независимого отзыва и ротации. Точные IAM-роли зависят от провайдера; проверить эффективные права на реальном объекте должен владелец хранилища.

API использует следующие параметры:

| Параметр | Назначение |
|---|---|
| INSPECTOR_BLOB_STORE=s3 | Выбор S3 |
| INSPECTOR_S3_ENDPOINT / INSPECTOR_S3_REGION / INSPECTOR_S3_BUCKET | Адрес и бакет |
| INSPECTOR_S3_PREFIX / INSPECTOR_S3_READ_PREFIXES | Основной и разрешённые исторические префиксы |
| INSPECTOR_S3_ACCESS_KEY_ID_FILE | Приватный файл идентификатора SA |
| INSPECTOR_S3_SECRET_ACCESS_KEY_FILE | Приватный файл секрета SA |
| INSPECTOR_S3_KEY_FILE | Отдельный существующий ключ AES-GCM корпуса |
| INSPECTOR_READONLY=1 | Серверный запрет изменений CPU-копии |

Поддерживаются AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY, но предпочтительны секретные файлы, смонтированные readonly. В stand Compose `S3_SECRETS_DIR` указывает каталог с access_key_id и secret_access_key. Не помещайте содержимое этих файлов в env-примеры, логи или базу знаний.

S3 credentials дают доступ к байтам; AES-GCM ключ расшифровывает байты. Это разные секреты. Новый SA может читать прежний корпус только вместе с правильным исходным ключом шифрования. Не заменять его ключом свежей установки. TLS CA/ключи, ключи БД и ключ оригиналов также сохраняются отдельно по назначению.

## CPU-кэш и проверка подключения

GPU-стартер принимает `--s3-env`, `--s3-key-file`, `--s3-prefix` и `--s3-read-prefixes`; пример находится в разделе развёртывания. `storage.json` сохраняет адрес и префиксы без значений credentials, `platform-s3.json` подключает API secret files. S3-ключ шифрования и отдельный ключ локального кэша сохраняются в state. Повторный запуск не генерирует замену существующим ключам; смена bucket/prefix/key требует явной миграции или ротации.

Перед включением оригиналов измерьте свободный диск и поведение кэша. При последнем срезе свободно 19 GiB, весь корпус около 22.9 GB; дисковый кэш не ограничен. До настройки лимита/очистки или предоставления достаточного места нельзя обещать устойчивый доступ ко всему корпусу. Не копируйте весь корпус и не удаляйте чужие файлы для освобождения места.

Проверьте небольшой и большой оригиналы, crop и протокол через приложение, сравните ожидаемые SHA и отсутствие ошибок расшифрования. Проверьте readonly запрет записи API и S3. Успешный список объектов не подтверждает расшифрование PDF.

## Согласованная резервная копия

Сохраните БД, оригиналы или проверенный доступ к бакету, все ключи, конфигурацию, закреплённые image/model revisions и исходный release manifest. Зафиксируйте SHA файлов и время снимка; для БД используйте согласованный dump, для SQLite — backup API или согласованный снимок, а не одиночный live-файл без WAL. Копию храните вне исходного хоста и отдельно от публичного архива. Пароли и приватные ключи передаются только владельцу.

## Восстановление в отдельной копии

1. Подготовьте новый изолированный state и сверяйте SHA перед использованием резервной копии.
2. Восстановите исходные ключи и конфигурацию; не запускайте генерацию новых ключей поверх старых документов.
3. Создайте отдельную БД/контейнер нужной версии. Для PostgreSQL проверьте состав: `pg_restore --list < backup.dump`. Восстановление ролей/схем выполняет оператор по приватному runbook конкретного снимка.
4. Восстановите оригиналы или readonly доступ к ним и закреплённые образы. Запустите стартер с восстановленным state: `sudo python3 scripts/platform-start.py --state /opt/inspector-platform`.
5. Сверьте старые строки по ID, количество документов и SHA оригиналов. Проверьте вход, PDF/crop, исторический протокол, новый процесс и экспорты на GPU; CPU должен сохранять запреты записи.

Не выполняйте DROP SCHEMA или восстановление поверх работающей базы. Сначала проверяется отдельная копия, затем согласуется переключение маршрута. Для отката сохраняйте прежние upstream и state. Стандартный GPU-стенд после передачи не выключается автоматически.
