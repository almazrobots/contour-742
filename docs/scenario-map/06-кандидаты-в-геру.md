# 06. Кандидаты в ГЕРУ

**Статус — предложение.** По правилу проекта требования пишутся только в `docs/gera/inspector/03-services.md`
и связываются с кодом в `model.yaml → impl`. Этот файл — не требования, а черновики формулировок для
решения владельца. После «да» правило переносится в модель, сначала пишется тест в `domain*.test.ts`,
затем `pnpm trace`.

**Основание каждого кандидата.** Закон ГЕРЫ: требование выводится из операции, операция — из обследования.
У кандидатов ниже источник — экспертная панель ([02](02-экспертная-панель.md)) и нормы, найденные ею.
Это **допущение**: панель не респондент. Для операций, которых нет в `02-business.md`, стадия 2 должна быть
пройдена заново — с источником SRC-INSP-08 «экспертная панель T-103» до появления живого инспектора.

## Новые правила существующих сервисов (стадия 3)

### OS-INSP-4.1 Принять решение по кандидату — партия с выборкой (SC-04, Н2)

- **OS-INSP-4.1.8** Система формирует партию только из записей NEGATIVE_VERIFIED, поставленных системой;
  в партию не входят критичные параметры Матрицы и значения, распознанные с уверенностью ниже 0,7.
- **OS-INSP-4.1.9** Система выбирает из партии k записей случайно со стратификацией по файлу и странице
  и сохраняет seed выборки.
- **OS-INSP-4.1.10** Если инспектор отметил в выборке хоть одну ошибку, система возвращает все записи
  партии в очередь на оценку.
- **OS-INSP-4.1.11** Когда инспектор принял партию без ошибок в выборке, система записывает на каждую
  запись партии решение с user_id, временем и ссылкой на акт приёмки партии, а в протокол — размер партии,
  k, seed и верхнюю 95 % границу доли ошибок.

### OS-INSP-4.1 — общий корень (SC-06, Н3)

- **OS-INSP-4.1.12** Когда инспектор отклонил кандидата с reason_code, система предлагает то же решение
  кандидатам этой проверки с той же сигнатурой корня; критичные параметры не предлагаются.
- **OS-INSP-4.1.13** Система записывает групповое решение поштучно: у каждого кандидата свои время,
  reason_code и ссылка на исходное решение; групповое подтверждение нарушения не допускается.
- **OS-INSP-4.1.14** Когда инспектор отклонил кандидата с причиной «неверная редакция», система пересчитывает
  эталон документа по OS-INSP-1.3 и снимает кандидатов, которых пересчёт не подтвердил.
- **OS-INSP-4.1.15** Пока протокол не финализирован, система позволяет инспектору вернуть решённого кандидата
  в статус CANDIDATE и пишет запись аудита. *(Нужно для отмены `Z`; сейчас `decide()` не умеет вернуть
  запись в ожидание.)*
- **OS-INSP-4.1.16** Система записывает для каждого решения число действий пользователя от показа кандидата
  до решения. *(Замер TZA-9.3.6-02 по данным, а не на глаз.)*

### OS-INSP-3.1 Сопоставить источники — граница ч. 1.3 ст. 52 (Н7)

- **OS-INSP-3.1.10** Когда на параметр зарегистрировано изменение РД, утверждённое застройщиком, система
  сравнивает с ним как с эталоном и записывает основание.
- **OS-INSP-3.1.11** Если параметр относится к несущим конструкциям, а изменение утверждено только
  застройщиком, система ставит CANDIDATE с пометкой «изменение касается несущих конструкций» и не
  предлагает причину «согласованное изменение».

### OS-INSP-3.3 Выпустить версию протокола — перенос решений (SC-10, Н4)

- **OS-INSP-3.3.5** Система сохраняет у каждого решения отпечаток доказательства: SHA-256 файлов, страницу,
  bbox, нормализованное значение и эталонную редакцию.
- **OS-INSP-3.3.6** Когда после дозагрузки отпечаток решения не изменился, система переносит решение в новую
  версию протокола с прежним автором и временем и пометкой; иначе возвращает запись в CANDIDATE.

### OS-INSP-1.4 Оценить комплектность — истребование (SC-03, Н5)

- **OS-INSP-1.4.5** Система вычисляет комплектность, перечень скрытых работ и реквизиты ИД до распознавания
  остальных страниц пакета.
- **OS-INSP-1.4.6** Система формирует черновик требования о представлении документов с пунктом Приказа
  № 344/пр и ссылкой на лист, из которого следует необходимость документа.
- **OS-INSP-1.4.7** Если вид документа не распознан, система не включает его в требование, а выводит
  отдельным перечнем «уточнить».

### OS-INSP-3.4 Выявить изменения листа — подпись словами (SC-09)

- **OS-INSP-3.4.5** Система подписывает область изменения разницей текста двух редакций в её bbox и
  сворачивает области внутри основной надписи и графы изменений в строку «служебные изменения».

### OS-INSP-4.3 Финализировать — окно отмены (SC-11)

- **OS-INSP-4.3.4** Когда инспектор финализирует протокол, система ждёт 10 секунд, в течение которых
  финализацию можно отменить без записи о финализации.

### OS-INSP-7.1 Изменить параметр Матрицы — предпросмотр влияния (SC-16)

- **OS-INSP-7.1.3** Перед выпуском версии Матрицы система показывает, сколько кандидатов на открытых
  проверках сменят статус.

### OS-INSP-2.3 Проверить реквизиты — поправка предметников

- **OS-INSP-2.3.5** Если рабочий чертёж подписан действительной электронной подписью (OS-INSP-1.2.12),
  система не требует штампа «В производство работ». *(Основание — СП 48.13330 п. 5.8, номер пункта сверить.)*

### Кандидаты по живым документам ([09](09-живые-документы.md))

- **OS-INSP-3.4.6** Система находит на листе РД облака изменений с номером изменения и использует их bbox
  как первую точку показа при сравнении с ПД.
- **OS-INSP-3.1.12** Когда параметр задан составом оборудования помещения, система сопоставляет листы ПД,
  РД и ИД по номеру помещения из экспликации и показывает «было → стало» по помещению.
- **OS-INSP-2.3.6** Если шифр РД в АОСР не совпадает с шифром в реестре и основной надписи, система ставит
  CLARIFICATION_REQUIRED по акту с обоими значениями.
- **OS-INSP-2.3.7** Если дата документа, на который ссылается АОСР, позже даты акта или отстоит от неё
  больше чем на год, система ставит CLARIFICATION_REQUIRED по акту с обеими датами.
