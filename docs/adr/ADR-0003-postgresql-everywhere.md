# ADR-0003. PostgreSQL во всех профилях

## Контекст

ADR-0001 разделял хранилище по профилям: SQLite (`node:sqlite`) на маке, PostgreSQL в эксплуатации, «переход — замена
адаптера». Адаптера не было: весь API (21 модуль, 240 запросов) писался против синхронного `DatabaseSync`, а в compose
профиля gpu PostgreSQL отсутствовал — стенд тоже работал на файле SQLite. Следствия, найденные аудитами 25–26.09:

- аудит стека — 🔴 «расхождение с ADR»: заявлен PostgreSQL, стоит SQLite (Stability 1.2, RC);
- OWASP H3 — ML монтирует том API на чтение и видит файл базы вместе с токенами сессий;
- синхронный доступ скрывал отсутствие транзакционной дисциплины: атомарность держалась на однопоточности, а не на БД.

Владелец (26.09): переписать на PostgreSQL и закрыть тему с БД.

## Решение

1. **Один движок — PostgreSQL 18 (актуальная ветка, поддержка до 14.11.2030) — во всех профилях.** PGlite 0.5.8 —
   PostgreSQL 18.3; сервер в compose — `postgres:18-alpine` 18.6 по digest; сервер паритета в гейте — 18.6. Разный SQL-диалект в dev и в эксплуатации означает, что
   эксплуатационный код не тестируется. Поэтому:
   - эксплуатация (gpu): сервер PostgreSQL, драйвер `pg`, пул соединений (`INSPECTOR_DATABASE_URL=postgres://…`,
     пароль — файлом `INSPECTOR_DATABASE_PASSWORD_FILE`); встроенная база в профиле gpu — отказ старта;
   - разработка и тесты: **PGlite** — тот же PostgreSQL 18, собранный в WASM, в процессе, без сервера и Docker
     (`pglite:var/pgdata` на маке, `memory` в тестах: база из снимка шаблона за миллисекунды, изоляция на тест);
   - паритет: весь набор тестов гоняется и на реальном сервере — `INSPECTOR_TEST_DATABASE_URL=postgres://…` открывает
     каждую тестовую базу свежей схемой на сервере (гейт, T-107).
2. **Асинхронный интерфейс `DB`** (`src/db.ts`): `all/get/run/exec`, `tx(fn)`; вложенная транзакция — SAVEPOINT.
   Плейсхолдеры родные (`$1`). Внутри транзакции код ходит только через её `DB`. Типы приводятся одинаково в обоих
   драйверах (`domain/db-core.ts::PARSERS`): bigint → number (вне безопасного диапазона — ошибка), timestamptz →
   ISO-строка, json → текст как есть.
3. **Схема — версионированные миграции** `apps/api/src/db/migrations/NNNN_имя.sql`: журнал `schema_migrations`
   с контрольной суммой; изменённая после применения миграция или миграция в базе, которой нет в коде, — отказ старта;
   каждая миграция в своей транзакции; параллельный старт реплик — под `pg_advisory_xact_lock`.
4. **Типы по назначению**: системное время — timestamptz; даты внешних систем и реестров — text как пришли; флаги —
   boolean; JSON — `json` (текст байт в байт: хеши протоколов и подписи не зависят от переформатирования, в отличие
   от jsonb); суррогатные ключи — identity; внешние ключи там, где родитель не удаляется, фрагменты доказательств
   удаляются каскадно, решение инспектора — след аудита и переживает пересчитанную проверку (без FK).
5. **Наименьшие привилегии в эксплуатации** (аудит БД 2026-09-26: HIGH-1, HIGH-4, M-1, M-2, M-5, M-8, M-9).
   - Роли (`deploy/gpu/postgres/init/10-roles.sh`, один раз при инициализации тома): `postgres` — бутстрап-суперпользователь,
     свой секрет, по сети не входит; `inspector_owner` (NOLOGIN) — владелец схемы `inspector` и её объектов;
     `inspector_migrator` — член владельца, по умолчанию `SET ROLE inspector_owner`; `inspector_app` — рантайм API:
     только DML в схеме `inspector` (default privileges владельца), без CREATE, без атрибутов суперпользователя.
     У каждой роли свой файл-секрет; API получает только пароль `inspector_app`.
   - Миграции, сиды справочников и первый администратор — одноразовая служба `api-migrate` (тот же образ,
     `node apps/api/dist/migrate.mjs`); `api` стартует после её успешного завершения. API в профиле gpu схему
     **не применяет, а сверяет**: непустой план или расхождение контрольных сумм — отказ старта «схема не накатана:
     запустите api-migrate». `schema_migrations` роли приложения — только на чтение. В dev и тестах (PGlite, паритет)
     миграции и сиды — в процессе, как прежде (`domain/db-core.ts::migrationMode`).
   - Демо-учётки (5 ролей, один пароль) — только в dev; в gpu пароль демо не вычисляется, файл `var/demo-password.txt`
     не создаётся. Первый `admin` в gpu — из секрета `INSPECTOR_BOOTSTRAP_ADMIN_PASSWORD_FILE`, только в пустую `users`.
   - TLS до базы: сервер `ssl=on`, TLSv1.3, свой `pg_hba.conf` (только `hostssl … scram-sha-256` для двух ролей,
     без TLS — reject); клиент — verify-full по CA стенда (`INSPECTOR_DATABASE_SSL_CA_FILE`, в gpu обязателен).
   - Пул: таймауты соединения и простоя, `statement_timeout`, `idle_in_transaction_session_timeout`, `lock_timeout`
     (служба миграций — без `statement_timeout`); те же значения — `ALTER ROLE inspector_app SET` на сервере.
   - Сеть `db` с `internal: true` — только `postgres`, `api`, `api-migrate`; журнал сервера — подключения, отключения,
     DDL, ошибки с оператором, в Logstash (gelf).
6. **Гейт висящих промисов** (`scripts/check-floating-promises.mjs`, в `pnpm test`): вызов async-функции без
   await/return/void — дефект; гейт проверен на фикстуре, где обязан краснеть.

## Последствия

- SQLite удалён из кода; `INSPECTOR_DB` упразднена (заданная — отказ старта с подсказкой).
- ML больше не видит базу: том `api-data` упразднён, ML монтирует только том блобов `api-blobs` на чтение
  (`/app/var/blobs`); демо-пароля и демо-учёток в gpu нет (снимает OWASP H3 и HIGH-4 аудита БД). Стенд с данными на
  старом томе `api-data` переносит `blobs/` в `api-blobs` один раз при выкатке.
- Compose профиля gpu: сервис `postgres` (digest, uid 70, read-only, cap_drop ALL, TLS, свой pg_hba, три секрета
  ролей, healthcheck по TCP — healthy только после init-скриптов), служба `api-migrate`; API стартует после healthy
  базы и успешных миграций.
- Смена пароля роли после инициализации тома — вручную (`ALTER ROLE` суперпользователем) и новый файл-секрет:
  init-скрипт повторно не выполняется.
- Данные dev-баз SQLite не переносятся: это синтетика, пересоздаётся `pnpm demo`.
- Вне этого решения, открыто: резервное копирование и PITR под RPO 15 мин (WAL-архив, T-072); шифрование в покое
  (T-071); RLS и отдельная роль только на чтение для отчётов — по мере появления потребителей.
