# ADR-0004. Объектное хранилище

## Контекст

ADR-0001 обещал S3 в проде, но не назвал ни провайдера, ни границы. 2026-09-26 владелец арендовал
Yandex Object Storage: бакет `nadzorium`, регион `ru-central1` (Москва), облако `src-user-cloud-almaz-qxp`.
Пока это хранилище данных владельца: ~150 ГБ с Яндекс.Диска заливаются постепенно через очередь `translog`.
Код api и ml к S3 не подключён: файлы по SHA-256 и веса лежат на томе `api-data`.

У заказчика закрытый контур, и S3 там будет его собственный (docs/plan/ORGANIZER-QUESTIONS-ENV.md, вопросы 10 и 20).
Значит, привязка к конкретному провайдеру в коде — долг, который придётся выкорчёвывать при поставке.

Решение принято сессией CTO 2026-09-26.

## Решение

1. **Код говорит только с S3-совместимым API.** Адрес (endpoint), регион, бакет и провайдер задаются
   конфигурацией. Имён Yandex и его SDK в коде нет. Yandex Object Storage `ru-central1` — наше хранилище
   данных и стенда. В контуре заказчика — его S3 по той же конфигурации.
2. **152-ФЗ.** Регион RU закрывает локализацию, но не защиту. **Пока нет шифрования на сервере (SSE-KMS),
   в бакет не кладутся ни ПДн, ни корпус ADR-0002.** Это условие, а не рекомендация.
3. **Бэкапы ТЗ 12.8** — на отдельном бакете или префиксе с версионированием и object lock (WORM).
4. **Порядок подключения.**
   - Первый потребитель в коде — бэкап PostgreSQL (T-072: WAL-G или pgBackRest → S3, RPO 15 минут, ТЗ 11 п.14).
   - Блобы — только по триггеру: второй хост или реплика API.
   - Тогда вводится интерфейс `BlobStore` (put, get, exists, verify по sha256) с реализациями `fs` и `s3`.
   - Ключи адресуются по содержимому и неизменяемы, удаление не нужно, поэтому API хватает роли загрузки и чтения.
5. **Паритет в гейте.** Локальный гейт проверяет реализацию `s3` на MinIO — по той же схеме, что PGlite
   и сервер PostgreSQL (ADR-0003).
6. **Права — по потребителю, на бакет.** Роль на весь каталог слишком широка. У каждого потребителя
   (заливка владельца, API, бэкапы) свой сервисный аккаунт с доступом только к своему бакету или префиксу
   через политику бакета. Удаление не выдаётся никому, кроме явно обоснованных случаев.
7. **Ключи.** Статические ключи — только в `.secrets/` вне git или в секретах стенда. Ключ, который побывал
   в чате, логе или контексте агента, считается скомпрометированным и перевыпускается сразу.

## Последствия

- В схеме C4 S3 — «есть, не в коде» (docs/architecture/C4.md, ARCHITECTURE.html).
- Противоречие «ADR-0001 обещает S3» закрывается частично: хранилище есть, интеграция — по п. 4.
- Для ПДн и корпуса нужен KMS-ключ (платный) и SSE по умолчанию на бакете — отдельная задача перед первой такой загрузкой.
- Сервисный аккаунт заливки владельца — `nadzorium-s3`, доступ политикой бакета `nadzorium` (T-108).

## Условия пересмотра

- Заказчик отвечает, что S3 в его контуре нет, или требует конкретное хранилище, несовместимое с S3 API.
- Появляется требование держать ПДн в S3 — тогда сначала SSE-KMS, затем пересмотр п. 2.
