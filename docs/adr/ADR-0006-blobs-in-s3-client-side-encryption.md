# ADR-0006. Блобы в S3 с шифрованием на клиенте

## Контекст

ADR-0004 вводит `BlobStore` «по триггеру второго хоста» и запрещает класть ПДн и корпус в бакет без SSE-KMS.
27.09 владелец поставил задачу T-129: подключить S3 к сервису и прогнать через систему реальный пакет
«Алтуфьевское ш., 79Б» (ПД и РД со штампами, где есть ФИО — это ПДн). У сессии нет доступа к консоли
KMS, а ждать его — сорвать задачу до стоп-кода 29.09. Решение принято сессией CTO.

## Решение

1. **`BlobStore` вводится сейчас** (п. 4 ADR-0004 досрочно): `put`, `get`, `exists`, `verify` по SHA-256.
   Реализации: `fs` (профиль dev, тесты) и `tiered` — локальный кэш-том плюс копия в S3. ML читает файлы
   с того же кэш-тома, что и раньше; API перед разбором гарантирует, что файл есть в кэше, и при промахе
   поднимает его из S3. Так ML не получает ключей S3 и не меняется.
2. **Шифрование — на клиенте, AES-256-GCM**, ключ 256 бит из файла (`INSPECTOR_S3_KEY_FILE`, вне git).
   Объект в бакете — `nonce ‖ шифротекст ‖ тег`; SHA-256 открытого текста — ключ объекта и метаданные.
   При чтении тег GCM проверяет целостность, затем пересчитывается SHA-256 открытого текста.
   Это строже SSE-KMS: провайдер не видит открытого текста вовсе. Условие п. 2 ADR-0004 («без шифрования
   ПДн и корпус не кладутся») выполняется. SSE-KMS на бакете остаётся желательным вторым слоем, не условием.
3. **Ключ объекта** — `blobs/<sha256>`; объект не перезаписывается (перед записью — `HEAD`). Удаление не нужно,
   поэтому хватает роли загрузки и чтения.
4. **Отказ хранилища — громкий.** Если S3 недоступен при приёме, файл не принимается (503), запись о файле
   не создаётся: половинчатого состояния «в базе есть, в хранилище нет» не бывает.
5. **Паритет в гейте — MinIO** (п. 5 ADR-0004): тесты адаптера идут на MinIO в Docker; стенд — на Yandex Object
   Storage по той же конфигурации (`INSPECTOR_S3_ENDPOINT`, `_REGION`, `_BUCKET`, ключи файлами).
6. **Корпус ADR-0002** по-прежнему в бакет не кладётся. Пакет «Алтуфьевское 79Б» передан владельцем для
   обкатки явно (T-129) и в репозиторий, тесты и демо не попадает.

## Временные отступления (долг)

- Пока у API нет своего сервисного аккаунта (п. 6 ADR-0004), стенд пользуется ключом `nadzorium-s3` с префиксом
  `blobs/`. Замена — только новый файл ключа: код и конфигурация не меняются. Нужен аккаунт `nadzorium-api`
  с ролью на бакет — действие владельца в консоли.
- Ключ `nadzorium-s3` побывал в чате (T-108, п. 7) и подлежит перевыпуску — действие владельца.

## Последствия

- NFR-OBJSTORE переходит из «эксплуатации» в прототип и стенд; C4 и ARCHITECTURE.html обновляются.
- Потеря файла ключа шифрования = потеря данных в бакете: ключ хранится вместе с секретами стенда и в
  резервной копии секретов владельца.

## Принятый риск (OWASP-аудит T-129, SEC-11)

Ключ объекта в бакете и его метаданные — SHA-256 открытого текста. Провайдер хранилища не может прочитать документ, но
может подтвердить, что у нас лежит известный ему файл (сравнив хеш). Принято для стенда и прототипа: содержимое
зашифровано, подмена объекта ловится сверкой SHA-256 после расшифровки. При выходе в прод с внешним провайдером ключ
объекта становится `HMAC-SHA256(k2, sha256)`, метаданные `sha256` убираются.

## Условия пересмотра

- В контуре заказчика есть KMS и он требует SSE-KMS вместо шифрования на клиенте.
- Появляется второй хост API: тогда кэш-том перестаёт быть общим, и ML получает собственное чтение из S3.
