## Находки

**Н-1 (RED) OS-INSP-6.5.5 — стенд не сравнивает время с пределами §11.**
`scripts/bench-11.mjs` пишет в `var/bench-11.json` мс, p50/p95/p99 и экстраполяции, но в нём нет констант пределов §11 (120 с, 180 с, 600 с, 30 с, 200 мс и т. п.) и нет вердикта pass/fail. Сравнение, видимо, делается руками в `docs/qa/PERF-11.md` — это документ, а не система. Code-ref `ml/synth/bench_pages.py::def page` рисует синтетическую страницу — к замеру он не относится. В impl нет ни одного теста.
Как проверить: `grep -n "200\|limit\|pass" scripts/bench-11.mjs` — порогов нет; в model.yaml у OS-INSP-6.5.5 нет ключа `tests`.

**Н-2 (YELLOW) OS-INSP-8.2.1 — «каждое действие» журналируется не полностью, тест на IP пустой.**
- `POST /api/v1/auth/logout` (app.ts:117-120) — audit не вызывается.
- `POST /api/v1/inspection/:id/sync` (app.ts:391-396): ручной перезапуск отправки не журналируется.
- `verifyBlobs` (integrity.ts:60) пишет в audit_log напрямую, без ip_address и user_agent, даже когда проверку запустил администратор через API.
- Чтения (протокол, файлы, журнал аудита) не журналируются. Нужно ли это — зависит от трактовки ТЗ 12.4, но буквально правило говорит «каждое действие».
- Тест: `expect(audit[0]).toHaveProperty("ip_address")` (e2e.test.ts:~248) проходит и при `ip_address = null`.
Как проверить: сделать logout и sync, затем `GET /api/v1/audit` — записей нет.

**Н-3 (YELLOW) OS-INSP-7.1.1 — правка порогов небезопасна и частично не работает.**
- `compare: z.any()` (app.ts:418): администратор может записать произвольный JSON, compare.ts упадёт или поведёт себя непредсказуемо при следующем разборе.
- app.ts:430-433: если min_value не null, compare_json всегда становится `{kind:"min"}`, и новый max_value не применяется. Если min_value выставить параметру вида decrease/equal (104 из 132), вид сравнения молча меняется на абсолютный минимум.
- Пороги delta_pct (10 параметров) меняются только через тот же невалидируемый `compare`.
- Тест проверяет один сценарий: min_value на параметре, у которого уже вид min. Ссылки (sp/gost/fz) и is_active не проверяются.

**Н-4 (YELLOW) OS-INSP-6.1.3 — хеш выборки не фиксирует её содержимое.**
gold.ts:43-44 хеширует отсортированный список finding_id. Если перевести решение из CONFIRMED в NEGATIVE, gold_label изменится, а хеш выборки нет, так что по хешу подмену метки не видно. dataset_version формируется в app.ts:520 (`gold-<дата>-v<n>`, где n = count+1; при параллельном выпуске возможна гонка), тестом не проверяется.
Как проверить: buildDataset с одним и тем же finding_id и разным verification_status → hashes совпадают.

**Н-5 (YELLOW) OS-INSP-7.3.1 — «редактировать» ограничено именем и основанием.**
PATCH /rules/:id (app.ts:484) принимает только is_active, rule_name, normative_base. condition, expected и fact_anchors — суть правила — после создания не меняются: остаётся только выключить и создать новое. Тест проверяет лишь выключение.

**Н-6 (YELLOW) OS-INSP-6.4.3 — «пять исходов для каждого из 132» не гарантируется и не проверяется.**
factory_v3.py:212 ставит «na» только параметрам с `applicability`, а docstring (стр. 3-4, 12-13) прямо говорит о «достижимых» исходах. Правило в 03-services.md обещает больше, чем делает код. coverage() есть, но ни один тест не проверяет по нему, что у каждого параметра есть все пять меток. В test_normal_na_and_conflict_objects_labels проверка NA (`… for c in appl if c in labels(g4)`) проходит вхолостую, если группы NA нет.

**Н-7 (YELLOW) OS-INSP-6.5.2 — coverage публикуется не для каждой метрики.**
Для precision, recall, f1, fpr, fpr_superseded, other_status_accuracy и low_quality_share `cov` = NaN (metrics.py:257-298), в report.json это null. Срезы object и param считаются с b=0 (run.py:452, 456), поэтому ДИ там нет, хотя TZA-14.3-07 требует ДИ по объектам. Тесты из impl проверяют только свойства бутстрапа. Сквозной test_eval_run_end_to_end_report проверяет n и ci, но не coverage, и в impl не указан.

**Н-8 (YELLOW) OS-INSP-6.5.1 — «связка» без ссылки и без теста.**
link_n/link_ok считаются в run.py:305-309 (сравнение множеств (object, stage, code, revision)), но code-ref указывает только на metrics.py, а юнит-теста на расчёт связки нет. Косвенно связку затрагивает только 6.5.4-тест: `n ≥ 1 и value не None`.

**Н-9 (YELLOW) OS-INSP-6.5.4 — «покрытие извлечения» по параметру в публикуемом отчёте не видно.**
В report.md по параметрам выводятся только value(n) из SLICE_METRICS (run.py:626-630), coverage есть только в report.json. Тест проверяет n и value связки для одного объекта (22 параметра), а не для 132, и coverage не проверяет.

**Н-10 (YELLOW) OS-INSP-6.3.2 — ссылка для отката не проверяется.**
rollback_to записывается (app.ts:554), но ни один тест его не проверяет, а механизма отката (эндпойнта, который возвращает предыдущую модель) нет. «Подпись ответственного» — это id пользователя с ролью supervisor, а не криптоподпись. Если ТЗ имеет в виду УКЭП, это расхождение.

**Н-11 (YELLOW) OS-INSP-8.1.2 — фильтры по статусу и датам не тестируются, граница `to` неточная.**
app.ts:270: `r.updated_at <= q.to + "T23:59:59"` — это строковое сравнение ISO, поэтому `…T23:59:59.500Z` > `…T23:59:59` и запись выпадает. Тест проверяет только `color=red` и `section=КР`.

**Н-12 (YELLOW) OS-INSP-6.2.1 и 6.4.1 — code-ref и тесты косвенные.**
6.2.1: code-ref — строка маршрута. Рекомендации есть только по причинам, у by_param их нет, хотя правило говорит «по reason_code и параметрам с рекомендациями». e2e проверяет только by_reason. 6.4.1: тест, который действительно проверяет штампы, печати, подписи и изменения (test_factory.py:92), в impl не указан.

**Н-13 (YELLOW, трасса) Ссылки на тесты — префиксы названий, а не полные названия.**
- `e2e.test.ts::администратор меняет порог без перекодирования` → фактически «…без перекодирования → новая matrix_version; инспектору — 403» (e2e.test.ts:383). Затрагивает 7.1.1 и 7.1.2.

Подстрочное совпадение pnpm trace, видимо, засчитывает, но под критерий «буквальное название» такие ссылки не подходят.
