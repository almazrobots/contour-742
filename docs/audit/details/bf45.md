## Находки

### RED

**OS-INSP-4.3.2 — MISSING_EVIDENCE можно превратить в нарушение через API.**
- `apps/api/src/services/inspections.ts:590-597` — `decide()` проверяет только статус процесса (`canVerify`) и `SPLIT`, а `finding_status` не проверяет. Очередь UI (`apps/web/src/pages/Verify.tsx:38`) фильтрует `finding_status === "CANDIDATE"`, но это не серверная защита.
- Сценарий: на объекте СЕВ (HW-2 = MISSING_EVIDENCE) инспектор отправляет `POST /api/v1/checks/<id HW-2>/decision {"action":"confirm"}` → 200, `verification_status=CONFIRMED_VIOLATION` → `buildProtocolBody` кладёт запись в `confirmed_violations` (protocol.ts:112, фильтр только по verification_status) → после финализации она уходит в «РиН» как подтверждённое нарушение. То же возможно для системных NEGATIVE_VERIFIED/NOT_APPLICABLE.
- Тест по ссылке («карточка кандидата…», e2e.test.ts:158) проверяет только, что ключ `missing_evidence` есть в `sections`. Ближе к правилу тест «скрытые работы…» (e2e.test.ts:176), но и он проверяет только попадание в перечень, а запрет превращения — нет.
- Code-ref `missing_evidence`: первое вхождение — счётчик `summary` (protocol.ts:134), а не раздел (protocol.ts:144).
- Как проверить: e2e — решение `confirm` по MISSING_EVIDENCE-записи должно давать 409/400. Исправление: в `decide()` отказывать при `finding_status !== "CANDIDATE"`.

**OS-INSP-5.2.3 — «решение не меняется при сбое» ничем не подтверждено.**
- Code-ref `«Решение инспектора не изменено»` — текст уведомления администратору (`apps/api/src/services/rin.ts:64`), а не логика.
- Тест «финализация…» (e2e.test.ts:245-284) после трёх неудачных попыток проверяет `status=FINALIZED, sync_status=SYNC_FAILED`, а `checks.verification_status` и `decisions` до и после сбоя не сравнивает.
- По коду поведение верное: `runDueSyncJobs` пишет только в `sync_jobs`/`inspections.sync_status`/`notifications`. Но мутация, которая добавит `update checks …` в ветку сбоя, не будет поймана.
- Как проверить: снимок `checks` и `decisions` по проверке до финализации и после SYNC_FAILED, сравнение на равенство (по образцу теста 5.4.7).

### Прочие наблюдения (вне вердиктов)

- **Уточнение «застревает».** `isOpenCandidate` считает CLARIFICATION_REQUIRED обработанным, поэтому последнее решение переводит процесс в COMPLETED. После этого `canVerify(COMPLETED)=false`, и повторно решить «Требует уточнения» нельзя, хотя `systemComment` обещает «до повторного решения инспектора». Сюда же относится невозможность исправить последнее решение до финализации.
- **Повторный split падает.** `splitCandidate` не проверяет `verification_status`: у уже разделённого кандидата finding_status = CANDIDATE, а новые id `${checkId}.N` конфликтуют по PK, в результате 500 вместо 409. Разделить уже подтверждённого кандидата тоже можно.
