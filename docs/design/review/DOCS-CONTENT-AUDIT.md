## Основные пробелы

- В navigation.json только два снимка: вход и Матрица. Для остальных операций нет визуальной опоры непосредственно рядом с действием.
- Тексты короткие, но почти не показывают конкретного результата, блокирующего состояния и восстановления после ошибки.
- Роль, стенд, версия и дата проверки описаны разрозненно. Нужен единый блок применимости и явные пометки режима просмотра.
- README ссылается на фиксированный коммит разметки; свежий компонент уже даёт более точные названия кнопок и состояния.
- Реестр и Trace Map описаны ссылками: пользователь не узнаёт, как найти актуальный план, его статус, владельца, версию и заменяющий документ.
- Текущая схема содержит только один объект screenshot на статью. Для последовательности действий нужны изображения внутри статьи, подписи, увеличение и связанный manifest.

## Четыре пакета для оценки и выполнения

Оценки ниже предварительные, в человеко-днях, при наличии запускаемой сборки и синтетических fixtures. Не являются оценкой всего редизайна сервисных страниц.

1. **Контракт актуальности и инвентаризация — 1–2 дня.** Выбрать сборку, проверить маршруты/роли/названия, завести статусы «проверено в интерфейсе / подтверждено кодом / требуется проверка». Выход: перечень источников по каждой статье и явные пробелы.
2. **Стенд для съёмки и комплект иллюстраций — 2–4 дня.** Подготовить безопасные PDF/XLSX/Word/XML, роли, ошибки и очереди; сценарии захвата, manifest и встроенные снимки. Выход: 25–40 уникальных кадров после объединения повторов; точное число уточняется сценарием.
3. **Переработка 16 статей и маршрутов — 3–5 дней.** Задача → применимость → действие со снимком → результат → ошибки; обновить словарь, FAQ, роли и маршрут к актуальным планам. Выход: матрица выше закрыта, нет неподтверждённых обещаний.
4. **Проверка руководства и актуальности — 1–2 дня.** Пройти ключевые маршруты нужными ролями, проверить ссылки/изображения/подписи, сверить план и реестр с владельцами. Выход: отчёт с датой/сборкой и оставшимися ограничениями.

Контракт и fixtures нужны до массовой съёмки. Тексты можно готовить параллельно с комплектом изображений; финальная проверка выполняется после интеграции в общий шаблон.

## Воспроизводимая съёмка

1. Фиксировать commit приложения, профиль стенда, язык, viewport, масштаб браузера, тему и версии fixtures. Рабочие документы корпуса не использовать; публичные примеры — синтетические либо отдельно разрешённые.
2. Создать отдельные учётные записи ролей и стабильные синтетические объект/пакет/параметр. Сброс состояния перед каждым сценарием предотвращает пустую очередь после разметки.
3. Каждый сценарий хранит роль, маршрут, seed, действия, ожидаемое состояние и имя снимка. Playwright ждёт готовности источника/шрифтов и завершения сохранения; случайные даты/идентификаторы контролируются fixtures.
4. Снимать общий экран и при необходимости отдельный читаемый фрагмент. Выделения и стрелки добавлять только для пояснения, с подписью; источники не заменять вымышленным интерфейсом.
5. Manifest связывает файл, статью, caption/alt, роль, сценарий, commit, fixture, дату проверки и основание публичного использования. Проверять пиксели и метаданные: пароли, токены, адреса, ФИО и содержимое приватного корпуса не публикуются.
6. Сохранять ошибочные состояния через локальные fixtures/контролируемый ответ API; не провоцировать сбои рабочего сервиса. В CI проверять отсутствующие файлы, ссылки и обязательные поля manifest.

## Конкретные риски устаревания

- Код DataVerification отличается от статьи: название начальной кнопки; отдельное corrected_value только для ответа Нет в reading; блокировка Да/Нет до готовности; истечение задания (409); обязательный комментарий независимого разбора. Это расхождения локального кода и текста, пока не подтверждённые на production.
- Ошибка получения следующего задания после успешного сохранения очищает карточку и сообщает «Ответ сохранён». Статья сейчас описывает только ошибку самого сохранения, при которой ввод остаётся.
- Роли интерфейса разметки: verifier/inspector/supervisor/admin/curator; управление — admin/curator. Нельзя переносить сюда названия ролей основной платформы без проверки.
- Число параметров, адреса стендов, клавиши, окно отмены, статусы РиН и тип обучения меняются независимо. Для каждого нужен источник и проверка при выпуске.
- Скриншоты CPU-демо не подтверждают операции рабочего модуля. Подпись должна указывать профиль, а статья — применимость конкретного действия.
- План/архитектурная схема с актуальной датой могут описывать будущее. Требуются статус, версия и ссылка на подтверждение реализации; дату файла нельзя считать доказательством актуальности.
