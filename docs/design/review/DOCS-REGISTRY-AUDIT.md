# Аудит каталога материалов, планов и служебных страниц

Дата: 2026-09-29. Основание: локальный код и документы; публикация на сервере не проверялась. Это набор задач для оценки, без внедрения.

## Что обнаружено

- `scripts/demo-docs.mjs:19`: семь групп, 20 явно включённых позиций каталога: руководство (1), BI-макет (1), ГЕРА (3), методика (7), подход (4), дизайн (1), результаты (3). Внутри руководства отдельно генерируются 16 статей. `docs/plan` в опубликованный список не входит.
- `SECTIONS` содержит только путь, название, источник и описание; на карточках нет владельца, версии, статуса и даты проверки отдельного материала.
- `publication.json` уже различает дату данных (`published_at`) и обновление материалов (`docs_published_at`), а также ревизию данных и сайта. Эти даты нельзя выдавать за дату проверки конкретной статьи.
- Markdown-рендерер удаляет front matter; относительные ссылки заменяет некликабельным `span.ref`. Это препятствует переходам между материалами. Изображения Markdown не имеют отдельного обработчика.
- HTML-материалы копируются как самостоятельные файлы: общий CSS документации их автоматически не унифицирует.
- В `docs/plan` есть draft, proposed, proposal, in-progress и документы без статуса. Название FINAL не означает действующий план: `RESET-2026-09-27.md` имеет draft и `supersedes_order_of`, а `TOP-20-FINAL.md` содержит прежнюю шкалу оценки, прямо названную архивной в RESET.
- В `docs/gera/TRACE-MAP-DESIGN.md` принят конкретный вариант оформления; источники эскизов и скриншотов указаны вне репозитория. Для публичной документации нужны разрешённые локальные изображения, а не ссылки на личные каталоги.
- Есть многочисленные QA-отчёты по отдельным задачам; публичный каталог включает только три результата, среди них T-129. Их актуальность относительно опубликованной ревизии требует отдельной проверки.
- `apps/web/src/pages/Files.tsx` — реестр рабочих файлов через API: поиск, фильтр обработки, 25 строк на страницу, раскрытие параметров и дозагрузка упоминаний. Это самостоятельный рабочий экран, а не каталог статей.

## Границы и правила

Каталог материалов отвечает «где инструкция, схема, решение, план, отчёт». Реестр рабочих документов отвечает «какой файл какого объекта обработан, какие факты извлечены». Их названия, навигация и статусы должны различаться.

Статус документа (черновик / предложен / действующий / архив) отделить от статуса выполнения задачи и от результата QA. Версию, источник, владельца и дату содержательной проверки показывать в карточке материала и статье. Неизвестное значение обозначать явно; время сборки не подставлять вместо проверки.

Текущий план выбирается явной подтверждённой ссылкой в манифесте, с владельцем, датой подтверждения и связанными задачами. Если подтверждённого источника нет, страница показывает «Действующий план не подтверждён», отдельно — проекты и история. Не выбирать план по имени FINAL или последней дате файла.

Публикация сохраняет явный разрешённый перечень. Не обходить все docs рекурсивно: внутренние ответы, персональные данные, исходный корпус и приватные документы не должны попасть на сайт.

## Небольшие партии публикации

1. **Основа:** REG-01/02, оболочка, каталог и один образец статьи со скриншотом; REG-12. Публичный эталон для последующих страниц.
2. **Практические материалы:** пользовательские инструкции (отдельный поток команды), исправления рендерера REG-05 и подтверждённая страница плана REG-04. При отсутствии подтверждения публиковать честное состояние, а не произвольный старый план.
3. **Схемы и методика:** Pipeline/Architecture и по 2–3 статьи методики/подхода за партию. В каждой партии содержательная и визуальная проверка.
4. **Интерактивная карта:** Trace Map отдельной партией с регрессионной проверкой режимов; общую оболочку применять через генератор `scripts/trace-map.mjs`.
5. **Качество и дизайн:** витрина прогонов, дизайн-система, BI-макет; архив вынести в отдельную группу.
6. **Рабочий реестр:** Files отдельным потоком после фиксации пользовательской границы «служебные страницы / сам интерфейс».

Критерий завершения: каждая разрешённая страница имеет понятную навигацию и единое оформление, каждый материал — проверяемый статус и происхождение; текущий план подтверждён; скриншоты соответствуют версии; интерактивные схемы и реальные рабочие данные сохраняют свои сценарии.

## Дополнение: коммерческая база знаний, видео и контракт актуальности

- **REG-13 (P0, M; зависит от REG-02):** единый манифест релиза связывает активный UI, документацию и медиа. UI-версия берётся из подтверждённого развёрнутого релиза/проверенного стенда; Git HEAD, `site_revision`, дата сборки и дата публикации не доказывают, что именно этот UI доступен пользователю.
- Для материала и медиа регистр хранит `scenario_id`, `ui_revision`, `docs_revision`, `media_revision`, `role`, `fixture_id`, `checked_at`, `check_id`, `outcome`, владельца и ссылки на доказательства. Фикстура — безопасный ID подготовленного сценария, без приватного payload. Проверка фиксирует окружение и фактически открытый UI-релиз.
- Статус медиа/инструкции `ready` означает проверенное соответствие сценарию последнего подтверждённого UI; `stale` — подтверждённое расхождение, `draft` — материал ещё не принят. Эти статусы отдельны от жизненного цикла исходного документа и выполнения задач.
- Пока UI-релиз не подтверждён, материал не получает `ready` и маркировку «актуальная версия». Разница SHA сама по себе не доказывает устаревание: изменение сценария, элементов или результата требует проверки и решения о пересъёмке.
- **REG-14 (P1, L; зависит от REG-13 и шаблона статьи):** каталог видео по задачам/ролям, видео внутри соответствующих инструкций; у каждого — название, длительность, ожидаемый результат, подтверждённая UI-версия, captions и доступная текстовая расшифровка. Транскрипт индексируется общим поиском, результаты ведут к статье и временному фрагменту видео.
- **REG-15 (P0, M; повторяется для релиза):** проверить все затронутые сценарии на последнем подтверждённом UI, назначить пересъёмку устаревших кадров/роликов, обновить captions/transcript и повторно проверить результат. Приёмка требует воспроизводимого сценария и проверки соответствия текст/кадры/UI.
- REG-02 расширяется этими полями; REG-03 показывает статус и фильтр видео; REG-05 отображает player, captions, transcript и таймкоды; REG-12 проверяет связность релиза, ссылки, captions и доступность. Новые партии сначала включают один принятый видеообразец, затем по 2–3 проверенных сценария.
- Публикация использует явный список разрешённых ресурсов и подготовленные безопасные данные. Проверяются изображения, звук, субтитры и транскрипты: персональные данные, токены, приватные URL и исходные payload не публикуются.
- Критерий коммерческого качества: единая навигация статей и видео, читаемые иллюстрации, удобный поиск по тексту и расшифровкам, доступный player; каждый опубликованный сценарий имеет проверяемую связь с подтверждённой UI-версией.
