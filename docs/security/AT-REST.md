# Данные в покое

**TL;DR.** Требование ТЗ 12.3-01 — «данные в покое (БД, файловое хранилище) зашифрованы». Оно закрыто четырьмя слоями:

- **База.** Том PostgreSQL лежит на устройстве LUKS. Стенд без этого не стартует.
- **Файлы пакета.** На диске они хранятся в формате IBE1 (AES-256-GCM с идентификатором ключа).
- **Копия в S3.** Шифруется на клиенте по ADR-0006.
- **Резервные копии и архив WAL.** Шифруются в CMS на сертификат получателя. Закрытого ключа на сервере нет.

## Что чем зашифровано

| Данные | Где лежат | Чем | Ключ | Проверка |
|---|---|---|---|---|
| БД PostgreSQL | том `postgres-data` | dm-crypt/LUKS (блочное устройство хоста) | ключ LUKS хоста | `deploy/gpu/at-rest-check.sh` из `deploy/gpu/up.sh` |
| Файлы пакета, fs | том `api-blobs`, `<sha256>` | AES-256-GCM, формат IBE1 (`domain/at-rest.ts`) | `INSPECTOR_BLOB_KEY_FILE` (секрет `blob_encryption_key`) | профиль gpu без ключа не стартует (`config.ts`) |
| Локальный кэш S3 | том `api-blobs` | то же, IBE1 | тот же | то же |
| Копия в бакете | S3 | AES-256-GCM на клиенте, ADR-0006 | `INSPECTOR_S3_KEY_FILE` | ADR-0006 |
| Открытый текст для ML | `blob-work` (tmpfs) | в памяти, на диск не пишется | — | при старте API в gpu проверяет по `/proc/self/mounts`, что это tmpfs |
| Базовые копии и WAL (T-136) | каталоги бэкапов и архива WAL | CMS AuthEnvelopedData, AES-256-GCM, RSA-OAEP или ECDH | сертификат получателя; закрытый ключ — вне сервера | `at-rest-encrypt.sh`, а сами каталоги — ещё и на LUKS (`AT_REST_EXTRA_PATHS`) |
| Прочие тома проекта (журналы ES, метрики, очередь) | тома compose | LUKS | ключ LUKS | `at-rest-check.sh --compose-project` проверяет все тома проекта |

### Формат IBE1 (локальные файлы)

`IBE1` (4 байта) ‖ `key_id` (8 байт) ‖ `nonce` (12 байт) ‖ шифротекст ‖ тег (16 байт).

- `key_id` — первые 8 байт SHA-256 ключа.
- Заголовок из магии и `key_id` входит в дополнительные данные GCM (AAD). Поэтому подмена `key_id` ломает тег, а не подбирает другой ключ.
- Имя файла — SHA-256 **открытого** текста. После расшифровки чтение сверяет хеш.
- Запись атомарная: временный файл рядом и `rename`.
- Формат объекта в S3 (ADR-0006, без заголовка) не меняется.

### Как ML получает файл

ML ключа не получает. Шифротекста тома `api-blobs` он тоже не видит. Файл для ML готовится так:

1. Перед `analyze`, `diff`, `measure` и `advise` API вызывает `BlobStore.localPath(sha)`.
2. `localPath` расшифровывает файл и проверяет SHA-256.
3. Затем кладёт открытый текст в `blob-work` — это tmpfs-том: у API он смонтирован в `/app/var/blob-work`, у ML — в `/app/var/blobs:ro`.
4. Когда объём превышает `INSPECTOR_BLOB_WORK_MAX_MB` (по умолчанию 1024), самые старые файлы вытесняются.

### Резервные копии и WAL

`deploy/gpu/backup/at-rest-encrypt.sh` шифрует поток stdin в каталог:

- `part-NNNNNN.cms` — части до 64 МиБ открытого текста. Каждая часть — отдельное сообщение CMS со своим CEK.
- `MANIFEST` — SHA-256 каждой части.
- `plain.sha256` — SHA-256 всего открытого текста.

Каталог появляется атомарно. При ошибке не остаётся ничего.

**Почему копия режется на части.** Замеры на OpenSSL 3.6.3, M4:

- Шифрование с `-stream` идёт потоком. 100 МБ — за 1,3 с, пик памяти около 7 МБ.
- `openssl cms -decrypt` читает сообщение целиком: около 5,5 × размера. Одно сообщение на 100 МБ заняло 560 МБ.
- С частями по 64 МиБ пик расшифровки — 410 МБ при любом размере копии. 100 МБ расшифровываются за 2 с.
- WAL-сегмент (16 МБ) — всегда одна часть.

**Повторная архивация WAL** сравнивается по `plain.sha256`: у GCM со случайным CEK шифротекст каждый раз другой. Для одного и того же содержимого `wal-archive-encrypted.sh` возвращает 0. Для другого содержимого — отказ без перезаписи.

## Ротация ключей

### Ключ хранения файлов

1. Сгенерировать новый ключ: `openssl rand -hex 32 > blob.key.new`.
2. Старый ключ дописать строкой в файл старых ключей. Затем смонтировать этот файл вторым секретом в `INSPECTOR_BLOB_OLD_KEYS_FILE` — override-файлом compose:

   ```yaml
   services:
     api:
       environment: { INSPECTOR_BLOB_OLD_KEYS_FILE: /run/secrets/blob_old_keys }
       secrets: [pg_app_password, rabbitmq_password, blob_encryption_key, blob_old_keys]
   secrets:
     blob_old_keys: { file: ${BLOB_OLD_KEYS_FILE:?} }
   ```

3. `BLOB_ENCRYPTION_KEY_FILE` указать на новый ключ и перезапустить api. После этого новые файлы пишутся новым ключом, а старые читаются по `key_id`.
4. Перешифровать старые файлы:

   ```sh
   docker compose run --rm api node apps/api/dist/cli/blobs-encrypt.mjs --rotate --dry-run
   docker compose run --rm api node apps/api/dist/cli/blobs-encrypt.mjs --rotate
   ```

   Затем повторный `--dry-run` должен показать «будет перешифровано: 0».

5. Убрать старый ключ из связки. После этого файл под неизвестным ключом даёт ошибку с `key_id` в тексте.

Локальный кэш S3 при неизвестном ключе не падает. Он считает это промахом: поднимает объект из бакета и перезаписывает кэш текущим ключом.

### Наследие

Файлы, записанные до включения шифрования, лежат открытым текстом. Они читаются, а счётчик `atRestStats().legacyReads` растёт. Перешифровать их: `pnpm blobs:encrypt` (или `blobs-encrypt.mjs` без `--rotate`).

CLI работает так:

- сверяет SHA-256 до и после;
- заменяет файл атомарно;
- при повторном запуске ничего не меняет;
- повреждённое не трогает и возвращает код 2.

### Сертификат получателя копий

Новые копии шифруются на новый сертификат. Старые остаются на старом: закрытые ключи всех сертификатов хранятся у владельца, пока живут их копии.

## Восстановление

- **База из копии.** Нужны сертификат и закрытый ключ получателя — их приносят на время восстановления:

  ```sh
  at-rest-decrypt.sh -r получатель.pem -k закрытый.key -o base.tar.gz /backups/base/<дата>
  ```

  Затем обычный `tar` и `restore-drill.sh` (T-136).
- **WAL.** `restore_command = '/opt/backup/wal-restore-encrypted.sh %f %p'`, окружение `WAL_ARCHIVE_DIR`, `AT_REST_RECIPIENT_CERT` и `AT_REST_RECIPIENT_KEY`. Если сегмента нет в архиве — код 1, для PostgreSQL это штатный конец архива.
- **Файлы пакета.** Нужны ключ хранения и старые ключи (если ротация не завершена). Без ключа файлы на томе не восстановить, поэтому ключ хранится вместе с резервной копией секретов.

## Ограничения

- **Целостность копий не подписана.** CMS EnvelopedData даёт конфиденциальность. Подлинность — нет: сертификат открытый, и поддельную копию на него может зашифровать любой, кто пишет в каталог бэкапов. Защиту от подмены дают права на каталог и LUKS. Для подлинности нужна подпись отдельным ключом — это задача T-136.
- **Проверка тома видит только dm-crypt.** Нативное шифрование ZFS и шифрование, которое делает сам провайдер, `at-rest-check.sh` не распознаёт. Такой стенд запускается только с явным `INSPECTOR_AT_REST_WAIVER=<причина>`: обход пишет предупреждение, а не молчит.
- **Swap.** tmpfs может уйти в swap, поэтому swap хоста должен быть зашифрован (LUKS или отключён). Скрипт swap не проверяет.
- **Кэш разбора ML.** Кэш разбора ML (Redis) и кэш прочтений содержат извлечённый текст документов. Они лежат только на томах проекта, то есть на LUKS. Отдельного прикладного шифрования у них нет.
- **Магия IBE1 в наследии.** Открытый файл наследия, который случайно начинается с `IBE1`, узнаётся по совпадению SHA-256 и читается как наследие. У принимаемых форматов (PDF, DOCX, XML, изображения, подписи) другие сигнатуры.
- **Стенд на маке.** Стенд `deploy/stand` работает в профиле dev: ключ хранения там необязателен, диск мака защищён FileVault.
